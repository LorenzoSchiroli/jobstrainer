# K8s Phase 2 — API Autoscaling (HPA) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a CPU-based HorizontalPodAutoscaler to the API on the local kind cluster, with metrics-server and a reusable in-cluster load harness.

**Architecture:** Install metrics-server (kind-patched) so HPA can read CPU. Add an `autoscaling/v2` HPA for the `api` Deployment (min 1 / max 4 @ 70%) and remove the Deployment's hardcoded `replicas` so the HPA owns it. Provide an in-cluster k6 Job that drives real `/jobs/search` traffic to demonstrate scaling. Document everything in the k8s README.

**Tech Stack:** Kubernetes (kind), metrics-server, HorizontalPodAutoscaler (autoscaling/v2), k6, kubectl.

## Global Constraints

- Target cluster/context: `kind-jobstrainer` (single node).
- HPA target: **API only**. Do not add HPAs for frontend, worker, Postgres, OpenSearch, or ingestion.
- HPA bounds: **minReplicas 1, maxReplicas 4, CPU averageUtilization 70%**.
- API CPU request is `250m` and must remain set (it is the utilization denominator).
- `--kubelet-insecure-tls` is a **kind-only** metrics-server flag; document it as such.
- All new manifests live in `deploy/k8s/`.
- Commit style: no `Co-Authored-By` trailer.
- The realistic scale-up *run* requires a valid `GROQ_API_KEY` in `jobstrainer-secrets`; this is deferred and NOT a build/verification prerequisite for Tasks 1–4. Tasks verify wiring (metrics reported, HPA computes a real %, load Job launches and emits requests), not a full scale-up.

### Task 2: HPA + remove hardcoded replicas

**Files:**
- Create: `deploy/k8s/api-hpa.yaml`
- Modify: `deploy/k8s/api-deployment.yaml` (remove `replicas: 1`)

**Interfaces:**
- Consumes: metrics-server from Task 1; the `api` Deployment and its `250m` CPU request.
- Produces: an HPA named `api` that reports current CPU % against a 70% target.

- [ ] **Step 1: Create the HPA manifest**

`deploy/k8s/api-hpa.yaml`:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 1
  maxReplicas: 4
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

- [ ] **Step 2: Remove `replicas: 1` from the API Deployment**

In `deploy/k8s/api-deployment.yaml`, delete the `replicas: 1` line under the Deployment `spec:` (leave `selector`/`template` intact). The HPA now owns the replica count.

- [ ] **Step 3: Apply both**

```bash
kubectl apply -f deploy/k8s/api-deployment.yaml
kubectl apply -f deploy/k8s/api-hpa.yaml
```

- [ ] **Step 4: Verify the HPA computes a real target (this is the test)**

```bash
kubectl get hpa api
```
Expected: `TARGETS` shows something like `<N>%/70%` with a real number for `<N>` (e.g. `2%/70%`), NOT `<unknown>/70%`. `MINPODS=1`, `MAXPODS=4`, `REPLICAS=1`. Retry up to ~60s for the first computation.

- [ ] **Step 5: Commit**

```bash
git add deploy/k8s/api-hpa.yaml deploy/k8s/api-deployment.yaml
git commit -m "feat(k8s): add API HPA (min 1/max 4 @ 70% CPU) and let it own replicas"
```

### Task 3: In-cluster k6 load harness

**Files:**
- Create: `deploy/k8s/loadtest-job.yaml` (ConfigMap + Job)

**Interfaces:**
- Consumes: the `api` Service (`http://api:8000`).
- Produces: a `Job/api-loadtest` that ramps k6 virtual users against `POST /jobs/search`.

- [ ] **Step 1: Create the load manifest**

`deploy/k8s/loadtest-job.yaml`:
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-loadtest-script
data:
  load.js: |
    import http from 'k6/http';
    import { sleep } from 'k6';

    export const options = {
      stages: [
        { duration: '60s', target: 20 },
        { duration: '60s', target: 50 },
        { duration: '30s', target: 0 },
      ],
    };

    const payload = JSON.stringify({
      cv_text: 'Experienced machine learning engineer with Python, PyTorch, and NLP background. Built search and recommendation systems and hybrid retrieval pipelines.',
      query: 'machine learning engineer remote',
    });
    const params = { headers: { 'Content-Type': 'application/json' } };

    export default function () {
      http.post('http://api:8000/jobs/search', payload, params);
      sleep(1);
    }
---
apiVersion: batch/v1
kind: Job
metadata:
  name: api-loadtest
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: k6
        image: grafana/k6:latest
        args: ["run", "/scripts/load.js"]
        volumeMounts:
        - name: script
          mountPath: /scripts
      volumes:
      - name: script
        configMap:
          name: api-loadtest-script
```

- [ ] **Step 2: Validate manifest parses (dry-run)**

```bash
kubectl apply -f deploy/k8s/loadtest-job.yaml --dry-run=server
```
Expected: `configmap/api-loadtest-script created (server dry run)` and `job.batch/api-loadtest created (server dry run)`, no schema errors.

- [ ] **Step 3: Smoke-run the Job to confirm k6 launches and emits requests**

```bash
kubectl apply -f deploy/k8s/loadtest-job.yaml
# let it run briefly, then inspect
kubectl wait --for=condition=ready pod -l job-name=api-loadtest --timeout=90s || true
sleep 20
kubectl logs -l job-name=api-loadtest --tail=30
```
Expected: k6 banner + a running `http_reqs` counter climbing (requests are being sent to the api Service). Requests may return HTTP 500 while the Groq key is missing — that is acceptable for this smoke test; we are verifying the harness sends load, not that search succeeds.

- [ ] **Step 4: Clean up the smoke run**

```bash
kubectl delete -f deploy/k8s/loadtest-job.yaml
```
(Leaves the manifest in the repo; removes the transient Job/ConfigMap from the cluster.)

- [ ] **Step 5: Commit**

```bash
git add deploy/k8s/loadtest-job.yaml
git commit -m "feat(k8s): add in-cluster k6 load Job for API HPA demo"
```
